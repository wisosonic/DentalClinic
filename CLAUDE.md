## Stack and layout

- Monorepo with npm workspaces: `apps/api` (Express 5, TypeScript, Knex, Zod), `apps/web` (React 18, Vite, TypeScript, Redux Toolkit + RTK Query, MUI), `packages/shared` (Zod schemas and types).
- Database: SQLite file at `apps/api/data/` (gitignored), chosen so no server is needed. Must stay portable to MariaDB/MySQL: `DB_CLIENT=mysql` switches it. The original dump is [aya_clinic.sql](aya_clinic.sql).
- Ports: API 4000, web 5180 (strict; 5173 is used by another project on this machine). The Vite dev server proxies `/api` to the API.
- API layering per module: `routes → controller → service → repository`. Business rules go in services, not controllers.
- Machine: Windows 11, PowerShell primary shell. Use forward slashes in scripts and avoid bash-only syntax in npm scripts. Docker is installed but cannot run (WSL missing), so do not rely on it.

## Rules

### Database
- **Never edit `aya_clinic.sql`.** It is only read by `importDump.ts`. Schema changes go in a new numbered Knex migration registered in `src/db/migrate.ts`; never edit a migration that has already been applied anywhere.
- **Write portable SQL.** Everything must work on both SQLite and MySQL: use Knex's builder, `ref()`/`money()` helpers from `migrations/helpers.ts`, no partial indexes, no `RETURNING`, no SQLite-only or MySQL-only functions. Dates are `YYYY-MM-DD` strings, times `HH:MM`, timestamps `YYYY-MM-DD HH:MM:SS` UTC (use `sqlNow()`).
- Money is `DECIMAL(12,2)`. SQLite stores it as floating point, so round to cents in code and use `ROUND(SUM(x), 2)` in aggregates. Never sum across currencies; currency is stored per row.
- Use Knex parameter binding. Raw SQL only with `?` bindings, never string concatenation.
- After changing the import or schema, run `npm run db:import -- --reset` and check that verification passes (rows, money totals, FKs).
- Do not run destructive statements (`DROP`, `TRUNCATE`, bulk `DELETE`) against a database holding real data without asking.
- Financial rows use soft delete (`deleted_at`) and RESTRICT foreign keys, not `ON DELETE CASCADE`. Queries on patients, treatment offers and payments must filter `deleted_at IS NULL`.

### Security
- Passwords: bcrypt (`bcryptjs`), cost from `BCRYPT_COST` (12). Existing `$2y$` hashes work and are re-hashed on login if their cost is lower.
- Tokens live in httpOnly cookies only, never in localStorage. Refresh tokens are stored hashed and rotated on use.
- Every route is deny-by-default: `requireAuth(ctx)` then `requirePermission('module:action')`, with the permission added to the matrix in `lib/permissions.ts`. Patient-reachable routes must also call `assertPatientAccess` (`lib/ownership.ts`). State-changing requests need the CSRF header (already enforced for all of `/api/v1` except login and password reset).
- Validate all input with Zod at the route boundary (`schema.parse(req.body)` in the handler; errors become 400 automatically). Whitelist fields; never pass `req.body` straight to the database. Do not use `hpp` (breaks with Express 5).
- Never log passwords, tokens, or full patient details. Never return stack traces to clients.
- Never commit `.env` files, the SQL dump with real data, or credentials. Keep `.env.example` current.

### Code style
- TypeScript strict mode. No `any` without a comment explaining why.
- Match the style of the surrounding code. Keep comments short and only where the reason isn't obvious.
- API responses follow the plan: lists return `{ data, meta }`, errors return `{ error: { code, message, details? } }`.
- Use the API field name `amount` even though the column is spelled `ammount`; map it in the repository layer.
- Share types and validation schemas through `packages/shared`; do not duplicate them in both apps.

### Clinical rules
- Appointment times are the clinic's local time in `CLINIC_TIMEZONE`; compute "now" only through `clinicNow(env, ctx.clock())` and never with `new Date()` directly. Tests inject `ctx.clock`.
- Booking goes through `assertBookable` inside the same transaction as the write. An appointment occupies `[time, time + duration_minutes)`; two appointments overlap when each starts before the other ends (touching is fine), checked for the doctor (`DOCTOR_BUSY`) and for the dental unit (`UNIT_BUSY`). There are **no working-hours rules**: any day and time is allowed, but it must end before midnight. Active statuses are pending, confirmed, completed. Duration is 15 to 480 minutes in steps of 15; only a doctor or admin may change an existing appointment's length.
- Only doctors and admins may complete a visit or edit teeth (`visits:update`). Patients may only cancel their own appointment with notice (they may no longer book; see the owner decisions).
- Patient-facing responses omit `description` (internal notes), phone numbers of others, tooth notes, and `drPart`. Keep new DTOs consistent with that.
- Patients, treatment offers (the `treatment_offers` table) and payments are soft-deleted: add `whereNull('deleted_at')`, and join through `appointmentQuery()` for appointments so deleted patients stay hidden.
- Detect FK violations with `isForeignKeyError` (SQLite reports RESTRICT under `SQLITE_CONSTRAINT_TRIGGER`).
- SQLite uses one connection, so the concurrent-booking test cannot prove the MySQL `FOR UPDATE` path. Test it on MySQL before go-live.

- When you edit a file from a script, replace by slicing at `indexOf`, or pass a function to `replace()`: a `$` followed by a backtick, `&` or a digit in a replacement string is special and silently duplicates or mangles text (this corrupted this file once).

### Frontend
- **Settings (owner decision 2026-10-05):** not in the side menu. A **gear icon next to the language button in the header** (admin only) opens `/settings`, which shows its sections as a **vertical list down the side** (a scrollable row on phones) with the chosen section beside it: **General**, **Appearance**, **Taxes** (`features/settings/SettingsLayout.tsx`, routes `/settings/general|appearance|taxes`, `/settings` goes to General). A new section is one entry in `SETTINGS_SECTIONS`, one route in `App.tsx`, one entry in `SETTINGS_SECTION_LABEL` (breadcrumbs) and `SETTINGS_PATHS` (gear highlight in `AppLayout`), plus Arabic text. **General** (`GET/PUT /settings/general`, `modules/settings/app.ts`, table `app_settings` from migration 015, one text row per setting, no row = the default): the **default language** (applies only to people who have not picked one with the language button; `applyDefaultLanguage` never overwrites their choice), the **timezone** (the source for every date calculation: saving it updates `ctx.env.CLINIC_TIMEZONE`, which `clinicNow` reads; the server's `CLINIC_TIMEZONE` is only the starting default and is loaded once on the first request after a restart) and the **clinic contact details** (address, phone, email), which replace the clinic record's on the letterhead of the quote, receipt and visit-summary PDFs when set (`contactOverride`; empty keeps the record's). **Appearance** (`GET/PUT /settings/appearance`): **light or dark** and **text size** (small 13px, medium 14px, large 16px root) for the whole clinic, applied through `makeTheme(dir, { mode, textSize })` in `LanguageProviders`; there are no custom colours or fonts (owner decision, to keep the approved style). Both are served before sign-in by `GET /public-settings` (language, mode, text size only, no contact details or timezone) and the last look is remembered in the browser (`aya.look`) so the page does not flash light. **Not settings (owner decisions 2026-10-05):** no currency choice (still USD, plus LBP read by the tax page) and no notification switches yet (they come with phase 7). **Dark mode rules for new screens:** use theme colours (`background.paper`, `text.*`, `action.hover`, `divider`) and `useTheme().palette.mode`; never a hard-coded `#fff` or dark ink on a surface; chart colours need a validated dark pair (the monthly chart's is `#3f8ee6` / `#dc6a38`). Taxes holds the income tax rules.
- **Side menu:** `components/SideNav.tsx` holds the menu as groups (Clinic, Finance, Catalog, Administration) that fold away; a group with nothing the person may open is hidden, and the group of the current page opens by itself. A new page must be added to a group there (with its roles) and to `AppBreadcrumbs`; a new group needs an accent colour, an icon and an Arabic name.
- **Confirmations (toasts):** every successful change (a mutation) shows a short success toast at the bottom (`features/toast`). A new mutation endpoint **must be added to `TOAST_MESSAGES`** (English text, with Arabic in `i18n/ar/ui.ts`; a test checks it) unless a dialog already shows its result. Errors are not toasted: they stay inline where the action happened.
- **Compact sizing (owner asked for smaller components):** the theme uses a 14px root, 7px spacing, small inputs and tables by default, and 38px buttons on desktop (44px on phones). Do not enlarge components or set big fixed sizes in a screen; adjust `src/theme.ts` instead.
- **Breadcrumbs:** `components/AppBreadcrumbs.tsx` shows the trail above every page inside the layout. A new page must be added to its `SECTIONS` map (or get its own trail) and have an Arabic entry for its label.
- **Every table column that holds data is sortable** (the Actions column is the only exception). Use `SortCell` and `useSort` from `components/SortHead.tsx`. Paginated lists (patients, appointments) sort on the server: add the column to the endpoint's `sort` enum (whitelisted, with a stable tie-break) and test it; tables that show every row use `sortRows` in the browser.
- **Every new screen must follow the approved visual style** (owner approved it on 2026-10-02): use `PageHeader` for titles, `BRAND` and the theme in `src/theme.ts` (teal-to-petrol gradient, soft shadows instead of outlines, rounded cards, pill chips, gradient primary buttons), `BrandLogo`/`AuthCard` for branding, dark-gradient sidebar, and the dashboard patterns (stat tiles, status-edged cards) for summaries. Do not hard-code new colours or one-off styles; extend the theme if something is missing. **One corner radius everywhere** (`RADIUS` = 10px in `src/theme.ts`, the same as inputs and buttons): Paper/cards, dialogs, menus, alerts, tables, skeletons and the dashboard banner all take it from the theme, so do **not** set `borderRadius` on a Paper, Card or Skeleton in a screen; where a plain Box must match, use `borderRadius: 1` (which is 10px). Only decorative shapes (pill bars, chips, circles) have their own. Doctors are shown as "Dr." where a person's name is greeted.
- Mobile-first and responsive: tables become cards on small screens, touch targets at least 44px.
- Server state goes through RTK Query with tag invalidation. Redux slices only for auth and UI state.
- Route-level code splitting for heavy screens (calendar, charts, PDF preview).
- Accessible by default: labels on every input, keyboard-usable calendar and tooth chart.

## Owner decisions (recorded 2026-10-01)

The full table is in section 14 of the plan. The ones that affect code:

- `dr_part` is a **percentage**. `payments.remaining` is the offer's balance after that payment, **always computed by the server**.
- **Doctors have no fixed working days or hours.** Their availability is only their booked appointments: a doctor cannot have two overlapping appointments, and that is the only booking rule. Appointment length is **variable** (15-minute steps, default 30, changeable by doctor/admin). Done in code: `clinic_doctor.schedule`, `WORKING_DAYS`, `SLOT_MINUTES` and `lib/schedule.ts` are gone.
- **USD only.** One clinic. Roles: admin, doctor, staff (plus patient).
- **English and Arabic with right-to-left for the screens only; PDFs, reports, notifications, medication/procedure names, tooth and surface names and other medical terms stay English.** The translation layer is react-i18next with **the English text as the key** (`t('Save')`), so a string with no Arabic simply shows English. **Labels whose core is a medical term (Tooth, Teeth, Procedure(s), Medication(s), Prescription, Dose, Treatment plan(s)) also stay English in Arabic** (owner decision 2026-10-05): they have no Arabic entry and are listed in `i18n/ar/englishOnly.ts` (`ENGLISH_ONLY`), which the i18n test accepts and which it checks has no Arabic entry. A new such label still goes through `t()` and is added to that list instead of getting a translation; sentences around them stay Arabic. **Every new piece of UI text must use `t()`** (or `translate()` outside components) and get an Arabic entry in `apps/web/src/i18n/ar/` (`auth.ts`, `ui.ts`, `messages.ts`); `src/test/i18n.test.tsx` fails if a literal `t('...')` key or a fixed API error message has no Arabic. Use logical styling (`marginInlineStart`, `marginInlineEnd`, `paddingInlineStart`, `insetInlineStart`, `borderInlineStart`, `textAlign: 'start'`; **not** `ms`/`me`/`ps`/`pe`, which MUI does not understand and silently ignores), never hard-coded left/right; keep the tooth chart `dir="ltr"` and times/phones in `<bdi dir="ltr">`. Dates use `dateLocale()` (Arabic with Western digits). The API always answers in English: the app translates the message text, and builds the few sentences that contain times or statuses from `error.details` (`lib/baseQuery.ts`).
- **External specialists (two cases, always consider both):** (1) the patient is his own: full working access (manage the appointment, treatment offer, report, profile); (2) the patient belongs to an owner doctor and he treats them: he sees the appointment (name only, no phone, `patientVisible: false`) and writes the report, nothing else; profile, timeline, chart and the patient's appointments answer 404. All of this goes through `apps/api/src/lib/scope.ts` (`doctorScope`, `ownsPatient`, `involvedIn`, `canManageAppointment`); a doctor login not linked to a doctor profile sees nothing. Any new endpoint that returns patient data must use it.
- **Only doctors and staff create appointments** (admin can too). **Patients cannot book appointments online.** The portal is view-only plus cancelling their own appointment 24 h ahead. The API enforces this: patients get 403 on `POST /appointments`. Patient logins are created by staff invitation only. Notifications are in-app only: do not build email, SMS or WhatsApp yet, but keep the `Mailer`/channel interfaces.
- **Treatment offers and payments visibility (offers replaced quotes and plans, 2026-10-06):** an admin sees everything; a doctor sees and writes only the offers and payments of patients whose **primary doctor he is**, never another doctor's, owner or external (404, not 403); **staff read every offer (never its cost) and book its visits, but cannot create or change one and cannot browse payment history**, yet can **record** a payment (via a narrow lookup that returns only the chosen patient's open offers: title, price, remaining). The matrix in `lib/permissions.ts` has one module, `offers`, for all of this; every such route needs a test that one doctor cannot reach another's offer.
- **Visit reports:** at most **one report per appointment** (`reports.appointment_id`, to be made unique), and it is **optional** (completing a visit never requires it). The doctor prescribes medications inside it (`medication_report`), with per-tooth notes in `report_tooth`. **The treating doctor (the appointment's doctor) and admin may edit it, also after completion**, with every change in the audit log. **Readers:** the treating doctor, the patient's primary doctor, admin, staff (read only) and the patient; **no other doctor** (a doctor who is neither treating nor primary gets 404). Staff never edit. A patient sees their appointments as a **timeline, each with its report**, limited to the **summary and the prescriptions**: never `report_tooth` notes, patient `description` or any internal field; and only their own (`assertPatientAccess`).
- **A doctor's identity** is the link `doctors.user_id` (set by an admin on the doctor's edit form). Use `doctorIdFor(db, user.id)` / `accessChecker` in `modules/visits/access.ts`; a doctor login with no linked profile has no access to reports. Phase 5 quote and payment scoping ("a doctor sees only his own patients' quotes") must use the same link.
- Report text (summary, tooth notes, prescription notes) is health data: it never goes into the audit log (log field names or ids only) and the PDF and patient views contain the summary and prescriptions only. `report_tooth` notes are clinic-only (`patientSafe()` strips them).
- Medications are a prescribing catalog only: no stock tracking.
- **Deleting (owner decision 2026-10-02, replaces "never hard-delete"):** staff and doctors can only **soft delete** patients, appointments and reports (`deleted_at` and `deleted_by`; a doctor only what he can see, via `doctorScope`; money records join in phase 5). Soft-deleted items go to the admin-only **Trash** (`modules/trash`, page *Trash*). Only the **admin** can restore or **permanently erase** an item, and only from the Trash. Erasing also erases what is attached (a patient's appointments, reports with tooth notes and prescriptions, quotes, payments, plans, lab orders and their sign-in login) in one transaction, after a warning that lists the counts and a typed patient name (`CONFIRM_MISMATCH` otherwise). Every erase is audit-logged (`trash.purge`, counts only, never content). **Every query on appointments, reports or patients must filter `deleted_at`** (`appointmentQuery` and `loadReports` do). A deleted report blocks writing a new one (`REPORT_IN_TRASH`) until it is restored or erased. A restored appointment is checked against double booking. **Any new record type that is soft-deleted must be added to `trash/purge.ts` (footprint, counts, erase order) and the Trash page.**
- **Doctors are `owner` (Aya, Sara) or `external`** (`doctors.kind`, plus `doctors.commission_percent`). The percentage is required when an external doctor is created (the API and the form enforce it); an owner has none. Owner doctors and admin create/edit external doctors; **only admin creates or edits owner doctors** (enforced in `doctorsRouter`, since the matrix alone can't tell the kinds apart). The fee an owner pays a specialist is typed in each time. Quote `price` = amount quoted to the patient; `cost` = clinic's own cost.
- **Uploads:** only clinic logos so far (`PUT /clinics/:id/logo`, raw image body, admin only). The server identifies the image by its bytes (`lib/images.ts`; PNG/JPEG/WebP, never SVG), stores it under `UPLOAD_DIR` with a random name, serves it only to signed-in users, and deletes the old file on replace/removal/clinic delete. Any new upload must follow the same pattern. Static brand files live in `apps/web/public/` (`images/logo.png`).
- **Dental panorama (built):** one flat illustration of all 32 teeth (two rows of 16, like a panoramic X-ray), identical for every patient, **drawn in code** from `src/lib/panoramaZones.ts` (positions, kinds and crown outlines) by `components/DentalPanorama.tsx`, so what is drawn and what is clickable always match and there is no picture file or licence to manage. The patient's history is drawn over it (teeth with history amber, chosen teeth teal; `clickable='all'` to choose teeth in reports and the appointment dialog, `'marked'` to read history on the patient page). It replaced the old `ToothChart` and the stock `panoramic.jpg`, both deleted. Nothing is uploaded per patient. To change the look, edit the layout file; tests check all 32 teeth, symmetry, no overlaps and tap size.
- **Deleting a clinic (owner decision 2026-10-05):** it removes **only the clinic's record**. Its appointments and the dental units they were booked on **stay** (`appointments.clinic_id` and `dental_units.clinic_id` become NULL, `ON DELETE SET NULL`, migration 017, which rebuilds those two tables on SQLite) because they feed the payment, commission and tax figures; a unit nobody was ever booked on is deleted with the clinic; the clinic's doctor assignments go. Patients, quotes, payments, reports and plans never pointed at a clinic. **A record of a deleted clinic is read-only:** every change to such an appointment (reschedule, confirm, cancel, complete, no-show, procedures, teeth) and to its visit report, and renaming its unit, answers `409 CLINIC_DELETED` (`assertClinicExists`); it can still be read everywhere (timeline, lists, reports, PDFs, shown as "Deleted clinic") and deleted (an appointment goes to the Trash). **Admins see them on the page "Deleted clinics' data"** (`GET /clinics/deleted-data`, `/settings/deleted-clinics`) and can delete them there; a unit with appointments on it cannot be deleted (`UNIT_IN_USE`: commission is worked out from it). Any new query that joins appointments to clinics must **left join** and accept a null clinic. The audit entry of a clinic delete records only how many appointments and units were kept.
- **Roles and permissions (owner decision 2026-10-06; Administration > Roles, admin only):** the four roles stay fixed (admin, doctor, staff, patient); the admin changes **what doctor and staff may do**. `lib/permissions.ts` keeps the built-in table as the default (`DEFAULTS`); the admin's differences from it live in `role_permissions` (migration 018, one row per changed `module:action`, `allowed` 1 or 0; an empty table means the defaults) and are loaded into memory at start-up and after each save (`setPermissionOverrides`; one API process only, like the cron jobs), so **`can(role, permission)` always answers from the defaults plus the changes** and every `requirePermission` follows. `GET /roles`, `PUT /roles/:role` (the complete list of permissions wanted; only differences are stored), `POST /roles/:role/reset` (all admin only, `modules/roles`); audited as `role.update` (granted and revoked permission names only) and `role.reset`. **Limits, all enforced in the API:** admin and patient cannot be changed (admin always keeps everything; a patient's reach is ownership, not this table); `users`, `audit`, `trash`, `settings` and `roles` are never given to doctor or staff (`ADMIN_ONLY_MODULES`); **money and supplier modules (`quotes`, `payments`, `expenses`, `suppliers`) can be taken away but not given** (`REVOKE_ONLY_MODULES`), because who sees which record (a doctor's own patients, the narrow staff payment entry) is decided in the routes, so **a permission never widens record scope**; a role that can add, change or delete something in an area must also be able to view it (`READ_REQUIRED`). `/auth/me` returns `permissions` (the person's effective list) and the side menu hides a page the person holds none of its `can` permissions for (`SideNav` items); the API stays the real guard. **A new module must be added to the `DEFAULTS` table, to `AREA_LABEL` in `features/roles/RolesPage.tsx`, and (if it is money-like) to `REVOKE_ONLY_MODULES`** (`offers`, `payments`, `expenses` and `suppliers` are). Saved changes for the old `quotes` and `plans` modules became `offers` in migration 020.
- **Doctors page and menu (owner decisions 2026-10-06):** *Doctors* and *Clinics* are in the **Clinic** menu group (not Administration; *Deleted clinics' data*, Users, Roles, Trash and Activity log stay there). The Doctors page lists **owner doctors and external specialists in two separate tables** (only specialists have a Commission column).
- **Patient page layout (owner request 2026-10-06):** the patient page keeps only the profile and the dental chart. Its header uses `PageHeader` with **`actionsBelow`**: the button bar is always on its own row under the patient's name, so a long name never moves it (use the same prop on any page whose title can be long). **Appointments and reports** (the timeline) and **Documents** moved to pages of their own, opened by header buttons like Payments: `/patients/:id/appointments` and `/patients/:id/documents` (`features/patients/PatientSubPages.tsx`, sharing `PatientPageFrame`: patient name as the subtitle, a *Back to the patient* button, and a breadcrumb Patients > name > page in `AppBreadcrumbs`). **A page's primary action goes in the header beside the back button, as on the Payments page**: on the Documents page *Add documents* is there (the page owns the upload dialog's state and hands it to `DocumentsSection` through its `adding`/`onAddingChange` props; used on its own the section shows the button itself). The lists the patient page opens filtered to the patient (`/payments`, `/treatment-offers`, `/lab-orders` with `?patientId=`) get the same trail Patients > name > list (`PATIENT_LISTS` in `AppBreadcrumbs`) **and the same `BackToPatientButton`** in their header, as the patient's own pages; add a new such list in both places. A new per-patient section follows the same pattern: its own route, a button on the patient page, a breadcrumb entry, and the patient's access rules on the server.
- **Patient page and payments table (owner request 2026-10-06):** on the patient page the audit shortcut is an **icon button only** (the words "Who viewed this record" are its tooltip and `aria-label`), and admins and doctors get a **Payments** button (`/payments?patientId=`, shown as an "Only <name>" chip that can be removed; staff cannot browse payments). Every row of the payments table has an **icon button that opens the payment's treatment offer** (`/treatment-offers/:id`, `aria-label` "Open the treatment offer of the payment of <amount>"). New icon-only buttons need a tooltip and an `aria-label`.
- **Patient documents (owner decisions 2026-10-05; migration 021 `patient_documents`, `modules/documents`, a *Documents* page of its own, `/patients/:id/documents`):** admin, staff and doctors upload and read; patients see none. Kinds: x-ray, panoramic, CBCT, blood test, other (English in both languages). **Images (PNG, JPEG, WebP) and PDF only, 25 MB each, one file per request**: the file is the raw body of `POST /patients/:id/documents?category&title&takenOn&note&name&allowDuplicate`, identified **by its bytes** (`lib/files.ts` `sniffDocument`, never the name or the `Content-Type`; no SVG, HTML or archives; a CBCT study as DICOM or ZIP is not supported: add its report as a PDF or screenshots). Stored in `UPLOAD_DIR/documents` under a random `doc-<12 hex>.<ext>`, written before the row and removed again if the insert fails; the name is checked against a regex before any `sendFile`. An exact copy (sha-256) for the same patient is refused (`DUPLICATE_DOCUMENT`, override with `allowDuplicate=1`); at most 200 per patient (`TOO_MANY_DOCUMENTS`). **Who:** a doctor only for patients he may see in full (`ownsPatient`: an external specialist treating an owner's patient gets 404, like the profile); **the uploader and admin edit or delete** (others 403); a deleted patient's documents are hidden. `GET /documents/:id/file` serves it `private, no-store`, `nosniff`, a picture also with a sandboxing CSP, a PDF inline for the browser's own viewer (a sandbox would stop it), named from its kind and date, **never the original name**. Soft delete goes to the Trash (kind `document`); **erasing it, or the patient, deletes the file after the database commit** (`removeDocumentFiles`) and the warning counts documents. Audited as `document.upload|update|delete` (ids, kind and size only: **never the file name, title or note**, which may name the patient) and `document.view` (a view under the patient, once per ten minutes). The web upload dialog sends several files one after another with per-file kind, title and date, checks type and size first, and offers "Add it anyway" for a duplicate. Not built: thumbnails, linking a document to a visit in the screens (the API takes `appointmentId`), DICOM, and showing documents to patients (phase 8). `UPLOAD_DIR` now holds patient health data: back it up with the database, keep it out of any public web root and encrypt the disk.
- **Dental units:** a clinic has a unit for each owner doctor (created automatically on assignment); admins can add more (`POST /units`, owner must be an owner doctor assigned to that clinic; names unique per clinic, case-insensitive). Every appointment is on a unit (`appointments.unit_id`, required by the API, nullable in the database because SQLite can't alter it). A unit is created automatically when an owner doctor is assigned to a clinic. **A unit can't host two overlapping appointments, and a doctor can't have two** (both checks, in the same transaction).
- **Every patient has a primary doctor; a treatment offer belongs to one patient and may have visits by different doctors,** so an offer has no single doctor of its own (it shows the patient's primary doctor). The collecting doctor of a payment is the patient's primary doctor (store it as a snapshot on the payment).
- Patient of an **owner doctor** (Aya, Sara): outside specialists who treat them are a third-party service. The owner doctor pays the specialist for the service; the specialist pays nothing.
- Patient of an **outside specialist**: he collects the payments, and the owner doctors get a percentage of **what he actually collected** (never the offer's price), paid later as `commission` payments. The commission goes to the **owner of the dental unit** the appointment took place on (Aya's unit: Aya is paid; Sara's: Sara). Commission owed to an owner = percentage x payments collected for that specialist's appointments on that owner's unit, minus commission payments received from him.
- **Money, as built (phase 5 part one, now on offers):** `modules/finance` holds payments; the offer itself is `modules/offers` (see *Treatment offers* below). Payments point at an offer (`payments.offer_id` in the database, `offerId` in the API: **the table is `treatment_offers` since migration 023 and the columns that point at it, `payments.offer_id` and `appointments.offer_id`, are named so since migration 024 (with the indexes); both are plain renames that keep rows, ids and foreign keys, and the dump import maps the dump's `quotes` table and `quote_id` columns to the new names (`source: 'quotes'`, `rename`)**). The offer's balance and every payment's `remaining` are rewritten by `recalcOffer` in the same transaction as every payment or item change (oldest first). Paying **more than the price is allowed** (owner decision 2026-10-05: clients are sometimes generous): the offer counts as paid and every balance (`remaining` on the offer and on payments) is clamped at 0, never negative; the extra stays in the payments total. A payment sent to a `sent` offer makes it `accepted`. Visibility: **a doctor sees only offers and payments of patients whose primary doctor he is**; `moneyScope` + `limitToScope` in `finance/service.ts` do this for payments and money figures, `offerScope` for offers (staff and admin see all offers); use them for every new money query. Staff cannot list or read payments: they record one through `GET /payments/open-offers` (title, price, remaining only), and can edit or soft delete **only payments they entered** (`created_by`), seen at `GET /payments/mine`. A payment stores `collected_by_doctor_id` (the patient's primary doctor at that time), the doctor's share `dr_part` (percent, admin-visible only), `method` and `created_by`. Offers and payments are soft-deleted into the Trash (`kind` offer and payment in `modules/trash`).
- **Expenses and commission, as built (phase 5 part two):** `finance/expenses.ts`, `finance/commission.ts`. Expense types: personal (admin only: staff get 404 for them and 403 on creating one), clinic, lab (`model_id` = lab id), supplier (supplier id), commission (the specialist's doctor id plus an **optional** `appointment_id` (owner decision 2026-10-05); when a visit is given it is validated: the specialist treated it and the patient's primary doctor is an owner; with no visit the fee shows in the fees statement with no owner). Doctors see no expenses at all. **Commission owed** (owner decision): for each clinic payment collected for a patient whose primary doctor is an external specialist, the percentage `doctors.commission_percent` of the amount goes to the owner of the dental unit of the patient's **latest completed appointment on or before the payment date** (`commissionStatement`); it is owed minus commission payments received (type `commission`, `model_id` = paying specialist, `collected_by_doctor_id` = receiving owner). A missing percentage is reported (`missingPercentage`, owed = null), never guessed. Admin sees all; an owner sees what is owed to him; a specialist what he owes; staff nothing. Commission payments are recorded by admins and by an owner for himself only. **Who received a commission payment can be changed when editing it** (`PATCH /commission/payments/:id` with `ownerId`: an admin picks any owner, an owner only himself; it must be an owner; the specialist who paid cannot be changed; old payments with no receiver are fixed this way; the audit entry holds the new owner id, never the memo). The fees an owner pays a specialist (commission expenses) are a separate statement; the specialist owes nothing on them. Expenses, commission payments, quotes and payments are all Trash kinds (`modules/trash`).

- **Payments are money collected by a doctor** (type `clinic`: from a patient, must reference a treatment offer; type `commission`: from an outside specialist, no quote). **Expenses are separate** and have five types: `personal`, `clinic`, `lab` (names the lab), `supplier` (names the supplier) and `commission` (the owner doctor pays an outside specialist for treating the owner's patient; names the doctor and appointment). **A `commission` *payment* is money collected from a specialist; a `commission` *expense* is money paid to one.** Keep the two apart in code and UI. Payments: doctors, staff and admin create and edit; **only admin deletes** (soft delete, kept in the audit log).

- **Treatment offers (owner decision 2026-10-06: treatment plans and quotes are one thing; `modules/offers`, API `/treatment-offers`, pages *Treatment offers* in the Clinic group; migration 020):** an offer is what will be done (**items**, in order, per tooth and procedure, each with a binding `price` and an optional `cost`), what it costs, what the patient agreed to and what was paid. **The offer's `price` is always the sum of its items and its `cost` the sum of theirs** (`recalcOffer`; an offer with no items keeps whatever price it has until its items are edited), so there is no separate quote. **Three separate indicators, never mixed:** the **offer status** (`draft`, `accepted`, `cancelled`; **owner decision 2026-10-06: an offer is made in the chair after the patient agreed, so a new offer is `accepted` at once; there is no online sending, so no `sent`, `rejected` or `expired`**). `POST /treatment-offers` makes it `accepted` (it needs at least one item, `EMPTY_OFFER`, and tells admins, staff and the patient's primary doctor, `offerAccepted`) unless the body has `asDraft: true`, an unfinished offer that is not binding (no payments, no visits, no notification, may have no items) and is made final with `POST /:id/accept`; `POST /:id/cancel` closes one the patient is not going ahead with (draft or accepted; refused once anything is paid, `HAS_PAYMENTS`, or booked, `WORK_STARTED`); a cancelled offer cannot be edited, `NOT_EDITABLE`; migration 022 mapped `sent` to `accepted` and `rejected` and `expired` to `cancelled`, and the dump import does the same; the **payment state** (`unpaid`, `partly_paid`, `paid`) worked out from the payments (`paymentStateOf`); the **work state** (`not_started`, `in_progress`, `completed`) worked out from the items (`workStateOf`). Payments are only taken on an `accepted` offer (`OFFER_NOT_OPEN`). Visits are booked per item, only on an **accepted** offer, through `assertBookable` (`POST /treatment-offers/:id/items/:itemId/schedule`); an item follows its visit (booked, done, or back to to-do when the visit is cancelled, missed or deleted: `syncOffer`, also run when an appointment changes) and can be marked done by hand (`/items/:itemId/done`). The items are replaced as a list (`PUT /:id/items`, ids kept for existing ones); an item that is booked or done cannot be removed (`ITEM_IN_USE`) and the total cannot fall below what was paid (`PRICE_BELOW_PAID`). **Staff never see any cost** (offer or item, `toOfferDtos`); the PDF (`GET /:id/pdf`, `renderOfferPdf`) lists items and prices, the total and what was paid, never the cost, and is logged as `offer.pdf`. **Old data:** migration 020 turned every quote into an offer with one finished item (same id, same payments, totals checked) and merged any plan into its quote (`PLAN_TO_OFFER` statuses; `paid` and `partially_paid` became `accepted`, `pending` became `sent`); the dump import does the same through `db/offerDefaults.ts` (`applyOfferDefaults`). Lab orders are soft-deleted and live in the Trash with offers (kinds `offer`, `lab_order`). **Any new offer endpoint must use `offerScope`, `offerQuery` and `mayWrite`.**

- **Work flow of an offer (owner, 2026-10-06):** the doctor writes the offer after the consultation (every work starts `pending`), books visits from the offer page, and after each visit marks the works done. `POST /treatment-offers/:id/items/:itemId/schedule` takes `alsoItemIds` to cover **several works with one visit** (all must be pending, `ITEM_NOT_PENDING` otherwise; the page has a checkbox per pending work and "Book one visit for the N selected works"). `POST .../items/:itemId/done` works on a pending **or booked** work, `POST .../items/:itemId/pending` puts a booked or done work back (unlinks its visit, which stays on the calendar); both are for the doctor and admin only (`offers:update`) and audit-logged (`offer.item_done`, `offer.item_pending`). **A work marked done by hand stays done** whatever happens to its visit (`syncOffer` skips done items); completing a linked visit still marks its works done by itself.

- **Income tax (owner rules, 2026-10-03/05; Finance > Income tax, admin only):** everything in Lebanese pounds (LBP), whole pounds. Base = the year's payments only, counted like the Summary (clinic payments from patients plus commission received); **expenses are never deducted**. **Payments are only ever stored in USD** (owner decision 2026-10-05: no LBP records are saved; `POST /payments` always writes `$`), converted at the admin's rate; a row in any other currency (there should be none) has no rate, so it is listed as excluded and never converted. Steps, exactly (`calculateIncomeTax` in `packages/shared/src/tax.ts`, the one function used by the server and the page): (a) the year's payments in USD x the USD to LBP rate; (b) x the tax percentage (**35%** for dental services); (c) minus the family allowances (single + spouse if eligible + each eligible child); (d) not below zero; (e) the progressive brackets applied to that amount; (f) not below zero; (g) reported in LBP only. **Laws change, so the rules are data:** exchange rate, tax percentage, allowances and brackets are saved in **Settings > Taxes** (`/settings/taxes`, admin only) as sets that apply **from a year** (`tax_rule_sets`, migration 013; JSON in `settings`); the estimate for a year uses the latest set starting in that year or before, and before any saved set the owner's starting values in `DEFAULT_TAX_SETTINGS` are used and the page says so (rate 89,500 LBP per USD; allowances 450,000,000, +225,000,000 spouse, +25,000,000 per child; brackets 0-540M 4%, to 1.44B 7%, to 3.24B 12%, to 6.24B 16%, to 13.5B 21%, above 25%). Brackets must start at 0, chain with no gap and end open. **Each doctor's family details (`doctors.tax_spouse`, `tax_children`) are set by an admin on the doctor's profile** and are the starting point on the tax page, which can try others; the whole clinic is taxed as single with no children. `GET /finance/tax?year&doctorId` (taxpayer: the whole clinic or one doctor, by who collected the money), `GET /settings/tax`, `PUT|DELETE /settings/tax/:year`. Viewing is audit-logged (`tax.view`: year and taxpayer, never the figures). It is an estimate, not a tax return, and says so. **Declared and paid (owner rule, 2026-10-05):** rates, allowances and brackets change with the law, so a past year must keep the numbers it was filed with. The page's "Mark this year as declared and paid" (`POST /finance/tax/declare`, admin only) stores the server's own figures for that day (payments, family details, the rules in use, the result) as JSON in `tax_declarations` (migration 014; one row per year and taxpayer: the whole clinic, or one doctor), with the day paid, a note and who did it. From then on `GET /finance/tax` returns that stored copy and **never recalculates** that year: the page locks the family details and the what-if box, and only warns (`drift`) if the payments recorded for the year have changed since. A year cannot be declared twice (`ALREADY_DECLARED`), before it starts, while trying another amount, or while payments in an unknown currency are left out; the figures are never taken from the page. **Reopening (owner rule, 2026-10-05): only the current calendar year can be reopened** (`POST /finance/tax/reopen`, admin only; a past year answers `YEAR_LOCKED`, so a filed return never changes). The declaration is kept as a voided record (`voided_at`, `voided_by`, `active_scope` NULL, migration 016), the year is calculated live again, and it can be declared again later; every reopening is audit-logged (`tax.reopen`, never the figures). **PDF worksheet:** `GET /finance/tax/pdf?year&doctorId` (+ `spouse`, `children` while not declared), admin only, logged as `tax.pdf`; a declared year prints its stored copy.
